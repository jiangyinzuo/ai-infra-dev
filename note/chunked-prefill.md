**Chunked Prefill（分块预填充）** 是一种面向大语言模型（LLM）推理的调度优化技术。它的核心思想是**将一个长输入提示（Prompt）的预填充（Prefill）计算，拆分成多个较小的“块”（Chunk），分多次逐步处理，并与正在进行的解码（Decode）请求混合调度**。

要理解它的价值，需要先了解 LLM 推理两个阶段的固有矛盾。

### 🎭 核心矛盾：Prefill 与 Decode 的“性格不合”

LLM 推理分为两个阶段，它们的资源需求截然不同：

| 阶段 | 工作内容 | 特点 | 资源瓶颈 |
| :--- | :--- | :--- | :--- |
| **Prefill（预填充）** | 一次性处理整个输入 Prompt，生成第一个输出 token | **计算密集型**，延迟高，但能充分利用 GPU 算力 | GPU 计算能力 |
| **Decode（解码）** | 逐个 token 地生成后续内容，直到结束 | **内存密集型**，单步延迟低，但 GPU 算力常常闲置 | 显存带宽 |

传统的调度策略往往顾此失彼：
- **优先 Prefill**：能保证 GPU 算力被吃满，提升吞吐量。但一个长 Prompt 的 Prefill 会长时间占用 GPU，导致正在进行中的 Decode 请求被“饿死”，**产生生成卡顿（Generation Stall），尾延迟（Tail Latency）急剧升高**。
- **优先 Decode**：能保证生成流畅，但 Prefill 请求会被无限期推迟，GPU 的算力资源大量闲置，**系统整体吞吐量低下**。

### 💡 Chunked Prefill 的解法：化整为零，见缝插针

Chunked Prefill 的思路正是为了调和这一矛盾：

1. **拆分 Prefill**：不再一次性处理整个长 Prompt，而是将其切分成多个固定大小的 **Chunk（块）**。
2. **交错调度**：在每一个调度轮次（Iteration）中，系统将一个 Prefill Chunk 与若干个正在进行的 Decode 请求**打包成同一个批次（Batch）** 一起计算。
3. **填充空隙**：由于 Decode 阶段是内存密集型的，GPU 算力常有富余。将计算密集的 Prefill Chunk 塞进这些“算力空隙”中，就实现了**对 Decode 阶段闲置算力的再利用**。

通过这种方式，长 Prompt 的 Prefill 不再是一个不可中断的“巨石任务”，而是变成了可以被 Decode 请求随时打断和插入的“细流”，从而在**不显著牺牲生成流畅性的前提下，大幅提升系统吞吐量**。

### 📊 主要优势与潜在代价

**带来的好处**：
- **平衡吞吐与延迟**：有效缓解了优先 Prefill 带来的生成卡顿，在严格延迟约束下显著提升服务容量。
- **稳定延迟表现**：通过组合长短 Prompt，使每个调度步的计算量趋于均衡，降低了首 token 延迟（TTFT）和每 token 输出时间（TPOT）的波动性，**生成节奏更稳定**。
- **减少流水线气泡**：在分布式推理中，有助于减少设备间的等待空闲，提升整体效率。

**需要付出的代价**：
- **算术强度下降**：当 Chunk 较小时，Prefill 计算的算术强度（计算与内存访问的比值）会降低，可能影响 GPU 利用率。
- **Attention 重复计算开销**：每个 Chunk 在做 Attention 时，都需要重新读取之前所有 Chunk 累积的 KV Cache，这带来了一些额外的内存访问开销。

### 🛠️ 典型实现与演进

Chunked Prefill 并非理论构想，它已在主流推理框架中落地。
- **vLLM** 从 v1 版本开始**默认开启**了 Chunked Prefill 功能，用来平衡 Prefill 和 Decode 的负载。
- **Sarathi-Serve** 等系统是该技术的早期推动者，提出了结合“无停顿调度（Stall-free Scheduling）”的机制。
- 该技术本身也在持续演进，例如出现了**自适应 Chunk 大小**的策略（根据其他请求的解码延迟目标动态调整块大小），以及专门针对 Chunked Prefill 场景优化的 **CompactAttention** 等注意力机制，以解决其特有的效率瓶颈。

总结来说，Chunked Prefill 是一种务实的工程智慧，它通过**将长 Prompt 的预填充“化整为零”，与解码请求混合调度**，巧妙地调和了 LLM 推理中计算密集与内存密集两个阶段的矛盾，是构建高吞吐、低延迟 LLM 服务系统的关键技术之一。
